# 図付き徹底解説をHTML1本にまとめる

複数トピックを、図付きで「なぜこの形か」まで踏み込んで解説し、目次付きの1本の自己完結HTMLとして `Artifact` 出力する。器・深さ・図はそれぞれ別の道具が担うので、この手順はそれらを束ねるだけにする。

- 解説の深さ: `explain-design` skill の観点に従う。「何をするか」の言い換えで終わらせず、上位の原則・要件・不変条件に結び付けて「なぜこの形か」を語る
- 図: mermaid。`Artifact` がネイティブ描画するので外部ライブラリは使わない
- 器: `Artifact` ツール。書く前に必ず `artifact-design` skill をロードして投資量を見積もる

## 手順

1. **トピックを列挙する**。バッチの単位を決める。各トピックは1章になる。読み手・前提知識・到達させたい理解を一言で押さえる。

2. **章ごとに中身を作る**。`explain-design` に従い、各章で以下を満たす:
   - 「なぜこの形か」を上位の原則・不変条件と結び付けて語る。表面的な言い換えで終わらせない
   - 具体を1つ引く。コード断片・実際の値・失敗する反例のいずれか
   - 採用しなかった代替と却下理由を1つ残す

3. **図を入れる。理解が目的なら「3軸」を最低限そろえる**。図種を指定されていないとき、章ごとに1枚を内容へマッチさせるだけだと理解に穴が空く。仕組み・全体像を掴ませるのが目的なら、以下の3軸を**必ずカバーする**。足りない軸があれば図を足す。「どれか1枚」でなく「3枚そろえて初めて分かる」と考える。
   - **静的構造 — 何があり、どう関係するか** → `classDiagram`。登場する型・モジュールと、所有・依存・実装の関係。型の粒度が合わない主題では依存・関連を示すコード関係図（`flowchart` / `erDiagram`）でもこの軸を満たせる。読み手の頭の中に「地図」を作る。これが無いと個々の説明が宙に浮くため、**3軸の中でも最優先で、原則省略不可**。**各クラスには一行の概要を添える**。名前だけの箱は地図でなくただの目次になる。mermaid ではクラスブロックの先頭行に説明文を置く。**パッケージ・層の境界は `namespace` で領域分けする**。名前は実パッケージ名に対応させ、図とコードの往復を保つ。依存の矢印が層をどう流れるかが箱の並びだけで読めるようになる
   - **動的振る舞い — どう動くか、時間順** → `sequenceDiagram`。主要フローの呼び出し順・往復・分岐。構造図が「地図」なら、これは「筋書き」。処理の追跡はこれでしか見せられない。地図の上に筋書きを重ねて初めて追えるので、**静的構造の図を置いた解説では原則セットで付ける**。登場人物はクラス図の要素と名前を一致させる
   - **目的・境界 — 誰が何のために使うか** → ユースケース図。mermaid に専用記法は無いので `flowchart` でアクター→機能の矢印として描く。システムの外縁と利用者を示し、「なぜ存在するか」を最初に据える。これが無いと読み手は詳細から入って迷子になる

   主題に応じてさらに足す。**答えたい問いから表現を選ぶ**。表も図と同格の視点表現として使う:
   - 状態と遷移が主題 → `stateDiagram-v2`
   - データ構造・型・スキーマの関係が主題 → `classDiagram` / `erDiagram`
   - 依存・所有の全体像だけを俯瞰 → `flowchart` / `graph`

   | 問い | 表現 |
   |---|---|
   | 値がどう変わるか | 状態表。変数×イベントで値の変化を追う HTML 表 |
   | 何が何へ依存するか | 依存グラフ。`flowchart` / `graph` |
   | 並行した処理の順序 | 時系列。`gantt` か `sequenceDiagram` の `par` ブロック |
   | 主体が何をできるか | 権限行列。主体×操作の可否を並べる HTML 表 |
   | どの入力で分岐するか | 決定表。条件の組合せ×結果を並べる HTML 表 |
   | 失敗後にどこへ戻るか | 状態遷移。`stateDiagram-v2` にエラー辺と復帰辺を明示する |

   図は文章の言い換えでなく、文章で追いにくい関係を1枚で見せるために置く。3軸の省略可否は軸で差を付ける。**静的構造は原則省略不可**で、省けるのは対象の構造が自明なとき（単一関数、型が1つ、など）に限る。**動的振る舞いは静的構造とセットが原則**で、省けるのは動きが自明なとき（純関数・宣言的データだけ、など）。ユースケース図は主題と無関係なら省いてよい。いずれも**省いた軸はその理由を本文か報告に一言残す**（例: 「単一関数の解説なのでユースケース図は割愛」）。ユーザーが図種を明示したときはそれを最優先し、3軸規約はあくまで無指定時の下限。

4. **1本のHTMLに束ねる**。先頭に目次、以降を章立て。各章に `id` を振り目次からアンカーで飛べるようにする。長くなってよい。徹底解説が目的。

5. **`artifact-design` をロードしてから書く**。HTML本文だけを書く。`<!doctype>`/`<html>`/`<head>`/`<body>` は付けない。`<title>` は付ける。favicon 絵文字を指定する。

6. **Artifact に書き出す**。成果物の置き場は claude.ai の Artifact だけにする。ローカルの恒久ディレクトリには保存しない。
   - HTML はセッションのスクラッチパッドへ `Write` する。これは `Artifact` が file_path を必要とするための一時ファイルで、保管場所ではない。
   - その file_path を `Artifact` に渡して claude.ai 上へレンダリングする。発行される URL は既定で非公開、本人のみ閲覧可。第三者への共有はユーザーがページの共有メニューから行うもので、こちらから共有しない。
   - mermaid が実描画されるのは Artifact 上だけ。ローカルの `file://` では図は出ない。
   - 更新は同じ file_path に再出力して同一 URL へ差し替える。別テーマで作り直すときだけ新しい file_path にする。過去の版をディレクトリに貯める運用はしない。

## バッチが大きいときは Workflow で並列生成

- 2〜3トピックまではインラインで書く。Workflow は使わない
- 4トピック以上、または各章が重い調査を伴うなら Workflow で fan-out する。この skill 経由の Workflow 呼び出しは正規の opt-in
  - `pipeline` でトピックごとに「調査 → 章HTML生成」を回す。章HTMLは `<section id>` 単位の断片を返させる
  - 返ってきた章断片を目次とともに1つのHTMLへ結合し、スクラッチパッドへ書いて `Artifact` で1本書き出す
  - 章の粒度・見出し階層・図の有無を全章で揃える。揃わない章があれば log で明示する

## Artifact の制約チェック

`artifact-design` の詳細に従うが、最低限これは外さない:

- **自己完結**: CSPが外部リクエストを全遮断する。CSS/JSはインライン、画像は data URI。mermaidは内蔵描画なのでそのまま使える
- **テーマ対応**: ライト/ダーク両対応。`prefers-color-scheme` と `:root[data-theme]` の両方を効かせる
- **レスポンシブ**: 本文は横スクロールさせない。広い表・コード・図は各自 `overflow-x:auto` の枠内でスクロールさせる
- **favicon**: 絵文字1〜2字。再出力でも変えない

## 品質チェックリスト

- [ ] 各章が「なぜ」に踏み込んでいる。言い換えで終わっていない
- [ ] 各章に図が1枚以上あり、文章で追いにくい関係を見せている
- [ ] 理解目的なら3軸（静的構造=クラス図・動的振る舞い=シーケンス図・目的境界=ユースケース図）を最低限カバーした。省いた軸は理由を明示した
- [ ] 静的構造の図（クラス図かコード関係図）を置いた。省いたなら構造が自明であることを明示した
- [ ] クラス図とシーケンス図をセットで置き、登場人物の名前を一致させた。動きが自明で省いたなら明示した
- [ ] クラス図の各クラスに一行の概要を添えた
- [ ] クラス図をパッケージ・層の namespace で領域分けし、名前を実パッケージに対応させた
- [ ] 目次から全章へアンカーで飛べる
- [ ] 却下した代替が理由付きで残っている
- [ ] ライト/ダーク・横スクロールを実機幅で確認した
- [ ] バッチで章を省いた・粒度を落とした場合はその旨を本文か報告に明示した
